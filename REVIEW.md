# Разбор PublishController

## 1. Не хватает валидации

**Где:** `batch()`, строки 13–33.

**Проблема:** `post_ids`, `publish_reason`, `status` и `body` берутся из запроса без полноценной валидации. Проверяется только длина причины внутри цикла.

**Последствие:** Неверные данные могут вызвать ошибки PHP или БД, а повторяющиеся ID — повторную обработку постов.

**Исправление:** Добавить `FormRequest`: проверить непустой массив `post_ids`, целые уникальные ID и наличие постов, строку `publish_reason` с минимальной длиной и тип необязательного `body`. Если `status` остаётся во входных данных, ограничить допустимые значения.

## 2. Статус не согласован с датой публикации

**Где:** `batch()`, строки 30–34, 51–54.

**Проблема:** Статус задаёт клиент, а `published_at` всегда получает `now()`. При `status=draft` пост остаётся черновиком с датой публикации.

**Последствие:** Ответ учитывает такой пост как опубликованный, хотя его статус — `draft`.

**Исправление:** Для операции публикации устанавливать `status=published` и `published_at` на сервере.

## 3. Не определено поведение при частичном выполнении batch

**Где:** `batch()`, строки 18–54.

**Проблема:** Посты обновляются по одному без общей транзакции, а отсутствующие ID молча пропускаются.

**Последствие:** Часть записей может обновиться до ошибки. Клиент не получает понятного результата по каждому ID.

**Исправление:** Определить режим: all-or-nothing — транзакция и откат при отказе; partial success — обработка ошибок и результат по каждому ID с причиной отказа.

## 4. Лишние запросы чтения в batch

**Где:** `batch()`, строки 19, 30–37.

**Проблема:** `Post::find()`, загрузка `user` и `comments()->count()` выполняют отдельные запросы внутри цикла.

**Последствие:** Большой batch создаёт много SQL-запросов и долго выполняется.

**Исправление:** Получить посты через `whereIn` с `with('user')` и `withCount('comments')`. В цикле использовать загруженные данные и `comments_count`.

## 5. N+1 при построении отчёта

**Где:** `report()`, строки 59–64.

**Проблема:** После загрузки постов `$post->user` и `$post->comments` запрашивают связи отдельно для каждого поста.

**Последствие:** Обычно получается `1 + 2N` запросов, что замедляет отчёт.

**Исправление:** Заранее загружать связи через `with(['user', 'comments'])`.

## 6. Отчёт загружается без пагинации

**Где:** `report()`, строки 59–75.

**Проблема:** `Post::all()` загружает всю таблицу, затем для всех постов загружаются комментарии.

**Последствие:** На большой базе отчёт потребляет много памяти и возвращает огромный ответ.

**Исправление:** Заменить `all()` на `paginate()` с ограниченным размером страницы и возвращать метаданные пагинации.

## 7. Нет проверки доступа к публикации

**Где:** `routes/api.php`, маршрут `POST /publish/batch`; `batch()`, строки 18–34.

**Проблема:** Если endpoint должен быть защищён, сейчас на маршруте нет аутентификации, а в контроллере — проверки прав на выбранные посты.

**Последствие:** Клиент без авторизации может менять статус и содержимое постов по переданным ID.

**Исправление:** Если публикация требует прав, добавить middleware аутентификации и проверку через Policy или Gate.
